
| 名词                       | 一句话答案                                                   |
| ------------------------ | ------------------------------------------------------- |
| **混合检索**（Hybrid Search）  | 同时跑==向量检索和关键词检索==，再把两份结果合起来用                            |
| **BM25**                 | 搜索引擎的老算法：数字面出现==次数== + 给稀有词==加权== + 长文档==打折==，**不懂语义**  |
| **IDF**（逆文档频率）           | 一个词出现在越多文档里就越不值钱；只出现在 1 篇里最值钱                           |
| **倒排索引**（inverted index） | 从「词」查「哪几篇文档含它」的索引，BM25 靠它做毫秒级关键词检索（普通数据库是「文档→词」，它是反过来的） |
| **RRF**（倒数排名融合）          | 合成两路结果的办法：每篇得分 = Σ 1/(60+名次)，**只看名次不看分数**，因为两路分数量纲不同    |
| **召回**（recall）           | 从全库捞出候选的那一步，目标是「别漏」，一般捞 top-20~50                       |
| **精排 / rerank**          | 对召回来的候选重新打分排序，目标是「排对」，一般砍到 top-3                        |
| **双塔**（bi-encoder）       | 问题和文档**各自**编成向量再比相似度。快（文档向量能提前存），但整篇被压成一个向量，细节被稀释       |
| **交叉编码器**（cross-encoder） | 把问题和文档**拼成一条**送进模型，逐字互相看，直接输出一个相关分。准，但每个候选都要跑一次模型，慢     |
| **忠实度**（Faithfulness）    | 答案里有几句能在检索到的资料里找到依据 ÷ 总句数。低 = 在编                        |

- **LLM-as-a-judge**（大模型当裁判）：RAGAS 背后的做法，让一个 LLM 替你判「这条断言有没有依据」

#### BM25和RRF

##### `tokenize()`
 `tokenize()`（day6\看懂混合检索-BM25和RRF.py:83）是纯字符串分词，4 行核心代码：
```python
text = text.lower()                                          # ① 统一小写
latin = re.findall(r"[a-z0-9]+", text)                       # ② 英文/数字连串当一个词
han   = re.findall(r"[\u4e00-\u9fff]", text)                 # ③ 每个汉字单独一个词
bigram = [han[i] + han[i+1] for i in range(len(han)-1)]      # ④ 相邻汉字拼成两字词
return latin + han + bigram                                  # ⑤ 三列拼接返回
```
逐行解析（输入 "XR-2000 坏了怎么保修？AI 扩图 500 次"）：
1. `lower()` — 转小写，保证 XR 和 xr 算同一个词。
2. `re.findall(r"[a-z0-9]+", text)` — 正则规则 `[a-z0-9]+` 匹配「小写字母或数字连续出现 1 次以上」。`+` 是关键：`xr-2000` 中 `-` 不在字符集里，当分隔符把两端断开 → `['xr', '2000', 'ai', '500']`。`r"..."` 原始字符串，让 \ 不被 Python 提前转义。
3. `re.findall(r"[\u4e00-\u9fff]", text)` — \u4e00~\u9fff 是 Unicode 基本汉字区（chr(0x4e00)='一' … chr(0x9fff)）。没写 +，所以每个汉字自成一词 → `['坏','了','怎','么','保','修','扩','图','次']`。
4. bigram 列表推导式 — 等价于：
   ```python
   bigram = [han[i] + han[i + 1] for i in range(len(han) - 1)]

   bigram = []
   for i in range(len(han) - 1):
       bigram.append(han[i] + han[i+1]) # '保'+'修'='保修'
   ```
`range(n-1)` 是因为最后一个字没有「下一位」。得到` ['坏了','了怎','怎么','么保','保修','修扩','扩图','图次']`。问号不在汉字区，已在上一步被丢掉，不会混进来。
- `latin + han + bigram` — 是列表拼接不是加法，结果约 21 个词，含重复。重复是故意的：看懂混合检索-BM25和RRF.py:116 里 toks.count(t) 要数 tf（词频），重复次数就是频次。
为什么不直接用世界级的 jieba？教学目的+零依赖。
两个正则实际覆盖了 BM25 需要的大部分信号（2000 这种型号不该碎成 `2/0/0/0`，保修 这种高频两字词靠 bigram 抓住）。要交互式逐行看打印效果，跑 day6\看懂tokenize.py 即可。

另：Python 标准库里还有个模块叫 tokenize（解析 Python 源码本身），与这里的分词概念不同词同名的撞击——名字撞了，模块那儿是拿源码切词牌。这里 tokenize 是自定义函数名，无冲突。

##### `bm25_scores`

bm25_scores（`day6\看懂混合检索-BM25和RRF.py:105-121`）就是标准 BM25 公式的直译版，分两段：
```python
def bm25_scores(query: str) -> dict:
    qt = tokenize(query) # ← 查询也切词
    idf = {}
    for t in set(qt):                                      # ← set 去重：每个词只算一次稀有度
        df = sum(1 for toks in TOKENS.values() if t in toks)   # ← 数：几篇文档含这个词
        idf[t] = math.log((N - df + 0.5) / (df + 0.5) + 1) # ← 越稀有分越大
    out = {}
    for k, toks in TOKENS.items():                         # ← 第二段：逐篇文档打分
        total = 0.0
        for t in set(qt):
            tf = toks.count(t)                             # ← 这个词在本篇出现几次
            if tf == 0:
                continue
            total += idf[t] * (tf * (K1 + 1)) / (tf + K1 * (1 - B + B * len(toks) / AVG_LEN))
        out[k] = total
    return out
```
合成一句话公式：`总分 = Σ 每个词的  稀有度 IDF × 饱和命中量 × 长度折扣 `
第一段：算 ==IDF（词的稀有度）==
- `sum(1 for toks in TOKENS.values() if t in toks)` — 生成器写法，含 t 的文档每篇产出 1，加起来就是 `df`（==文档频率==）。等价于 `sum(t in toks for ...)`。
- `idf = log((N-df+0.5)/(df+0.5) + 1)` — 两个 `+0.5` 是平滑防除零；
	- 右边 +1 保证 df 很大时结果仍是**正的小数**：
		- df=N（到处都是的词）→ log(0.111+1)≈0.105≈白送分；
		- df=0（一次没见过）→ log(10)≈2.30 最高。
- 注意 df=0 的词（如 Q1 里的「坏」4 篇全没有）IDF 冲到顶，但第二段里 tf=0 就 continue 了，贡献恰好是 0——稀有没用，得命中才行。
第二段：算 tf（命中强度，带饱和和长度惩罚）
分支里那坨分式，以`「len(toks)==AVG_LEN 的文档」`为基准展开：

| tf  | 贡献系数（没算idf）  |
| --- | ------------ |
| 1   | 1.00         |
| 4   | 1.82         |
| 8   | 2.11         |
| ∞   | → K1+1 = 2.5 |
`total += idf[t] * (tf * (K1 + 1)) / (tf + K1 * (1 - B + B * len(toks) / AVG_LEN))`：
- 分子 `tf*(K1+1)` / 分母 `tf+K1`：B=0.75、文档长度= 平均值时，分母就是 `tf+K1*1`。所以出现 1 次拿满 4 成收益，出现 8 次也才 84% ——出现越多分越高，但收益递减（饱和），防止堆词刷分。K1=1.5 就是调「递减坡度」的旋钮。
- `1 - B + B*len/AVG` 是长度归一因子：文档等于平均长度 → 1；比平均长 → 该因子 >1 → 分母变大 → 打折。B=0.75 是「打折力度」，B=1 全额罚、B=0 不罚。
几个工程上的点
- IDF 循环放前面独立算，是因为同一词要被 4 篇文档复用，先**算一次存 dict**，后面只查表——纯效率，不影响数学。
- `out[k] = total`：返回 `{文档: 分数}`，调用处（:153-157）对它 `sorted(..., reverse=True)` 得名次。
- 没命中的文档 total 保持 0.0，这就是脚本里说的「0 分之间排名无意义」。
一句话：第一段回答「**这个词值多少钱**」，第二段回答「**这篇文档挣了多少钱**」，**相乘再求和**就是 BM25 分数。和 rank_bm25 库、Elasticsearch 内部用的是同一个公式，只是把 K1、B 这些常量写死在文件顶（:101）方便教学。

###### bm25_scores

> 公式推导、idf 平滑、tf 饱和、长度归一化的**完整讲解在上文 `##### bm25_scores`**（demo 版，4 篇文档）。
> 这里只放**项目版代码**，和 demo 版的唯一差别是：不再依赖全局 `TOKENS` / `N` / `AVG_LEN`，改成把 `tokens` 作为参数传进来，这样任何一批块都能算。

```python
def bm25_scores(query: str, tokens: dict) -> dict:
    """
    输入：query；tokens = {块下标: [词, 词, ...]}
    输出：{块下标: bm25得分}（没命中任何词的块也会出现在结果里，分数 0）
    三步：
	    ① 每个词的 idf（越稀有越值钱）
	    ② 每块的 tf 加权（出现越多分越高，但收益递减）
	    ③ 长度归一化（长块打折，防止长文档天然占便宜）

    idf: 这个词的稀有度得分，中间表，用来给第二段查询用
    out：这个块的 BM25 总分，最终表，需要return出去
    """

    qt = list(set(tokenize(query)))          # 去重：同一个词只算一次
    n = len(tokens)
    if n == 0:
        return {}
    lens = {i: len(ts) for i, ts in tokens.items()} # 生成一张“块下标i → 该块词数len(ts)”的对照表
    avg_len = sum(lens.values()) / n
    # lens.values()拿到len(ts)，lens.keys()拿到i，lens.items()拿到键和值成对
    # sum=所有块的长度之和，然后/n 得到平均每一个块的长度

    # ① idf
    idf = {}
    for t in qt:
        df = sum(1 for ts in tokens.values() if t in ts)
        idf[t] = math.log((n - df + 0.5) / (df + 0.5) + 1)

    # ②③ tf 加权 + 长度归一化
    out = {}
    for i, ts in tokens.items():
        total = 0.0 # 为这一块准备一个分数累加器，初始值设为 0。
        for t in qt:
            tf = ts.count(t) # 统计这个词在这一块里出现了几次；0 表示没有出现。
            if tf == 0:
                continue # 如果这个词一次都没有出现，就跳过该词，使它不贡献任何分（idf 再高也用不上）
            total += idf[t] * (tf * (K1 + 1)) / (
                tf + K1 * (1 - B + B * lens[i] / avg_len)
            )
            # 计算这个词的贡献分——稀有度 × 饱和命中量 ÷ 长度折扣——并累加到 total。
            # 长度折扣：tf + K1 × 长度折扣因子，其中长度折扣因子根据「这块比平均长多少」折算
        out[i] = total # 存入总表，key:i, value:打分表
    return out
```

- `lens = {i: len(ts) for i, ts in tokens.items()}`：这一行的作用是**生成一张“块下标 → 该块词数”的对照表**，是字典推导式（`dict comprehension`，用一行写法创建字典）。

先看输入是什么：`tokens` 长这样（22 个块）：

| 键 | 值 |
|---|---|
| `0` | `['#','硬','件',...]`（该块切出来的词列表） |
| `1` | `['多','机','位',...]` |
| … | … |
逐段拆
```python
lens = { i: len(ts)   for i, ts in tokens.items() }
#        ↑    ↑         ↑   ↑      ↑
#        │    │         │   │      └─ 把「键+值」成对拿出来
#        │    │         │   └─ ts = 这一块的词列表
#        │    │         └─ i = 块下标（0,1,2...）
#        │    └─ 这一块有几个词
#        └─ 新字典的键
```
`lens = {i: len(ts) for i, ts in tokens.items()}`理解为：
- **`for i, ts in tokens.items()`** → 把每一项拆成「键 i」和「值 ts」 
- **`i: len(ts)`** → 新字典里，**键还是 i**，**值换成 len(ts)**
最后拿到的数据是这样的数据结构：`lens = {0: 210, 1: 99, 2: 262, ...}`，即 `{块下标: ts块的长度}` 组成的**字典（dict）**。

⚠️ 注意**不是** `[{...}]` —— `lens` 是字典，不是「装着字典的列表」。判断方法：`type(lens)` 是 `<class 'dict'>`，`lens[0]` 直接得 `210`（不是 `{'0': 210}`）。

##### 3. 零件：RRF

> 和 `看懂混合检索-BM25和RRF.py` 里的 demo 版**有一处关键差异**：demo 假设 4 篇文档两路都出现过，项目里两路召回的块并不一样，**必须处理「只在一路出现」的块**。

```python
RRF_K = 60                 # RRF 的 k，论文经验值

def rrf_fuse(vec_rank: list, bm_rank: list, k: int = RRF_K) -> list:
    """
    输入：两路的「块下标」有序列表（各自已按自己的分数降序排好）
    输出：[(块下标, rrf分), ...] 按 rrf分 降序

    只在一路里出现的块：另一路按「最后一名 + 1」计名次（不能丢，否则漏召回）
    """
    vec_pos = {idx: pos for pos, idx in enumerate(vec_rank, start=1)}
    bm_pos = {idx: pos for pos, idx in enumerate(bm_rank, start=1)}
    fallback_v = len(vec_rank) + 1      # 向量那路没召回 → 当它第 6 名
    fallback_b = len(bm_rank) + 1       # BM25 那路没召回 → 当它第 6 名

    fused = []
    for idx in set(vec_rank) | set(bm_rank):        # 两路的并集，去重
        score = 1 / (k + vec_pos.get(idx, fallback_v)) + 1 / (
            k + bm_pos.get(idx, fallback_b)
        )
        fused.append((idx, score))
    fused.sort(key=lambda x: x[1], reverse=True)
    return fused
```

逐行一句话：

| 行 | 意思 |
| --- | --- |
| `vec_pos = {idx: pos for pos, idx in enumerate(vec_rank, start=1)}` | 把「有序下标列表」反查成「块 → 名次」的明细表，`enumerate` 从 1 开始计名次 |
| `bm_pos = ...` | BM25 那一路同样处理 |
| `fallback_v = len(vec_rank) + 1` | 兜底名次：向量没召回的块，当成排第 6 名（5+1） |
| `fallback_b = len(bm_rank) + 1` | BM25 那一路的兜底名次 |
| `fused = []` | 准备空列表装「(块, 融合分)」结果对 |
| `for idx in set(vec_rank) \| set(bm_rank):` | 遍历**两路并集**——只在任意一路出现过的块都必须算进来 |
| `score = 1/(k + vec_pos.get(idx, fallback_v)) + 1/(` | 融合分 = 向量那份倒数 + BM25 那份倒数，`.get(键, 默认)` 查不到就用兜底名次 |
| `k + bm_pos.get(idx, fallback_b))` | 第二份：BM25 名次的倒数 |
| `)` | 闭合跨行括号（Python 靠 `()` `[]` `{}` 续行，不用反斜杠） |
| `fused.append((idx, score))` | 把「块下标 + 融合分」包成元组追加 |
| `fused.sort(key=lambda x: x[1], reverse=True)` | 按元组第 2 项（分数）降序，`lambda x: x[1]` = 取每对的第二个元素 |
| `return fused` | 返回 `[(20, 0.0323), (18, 0.0318), ...]` |

这一行里的三个新语法：

**① `.get(键, 默认值)`** —— 查字典但不怕缺键
```python
vec_pos[6]         # 块6不在向量那路 → KeyError 崩
vec_pos.get(6, 6)  # 块6不在 → 返回默认值 6，不崩
```
RRF 必须用 `.get`：两路召回的块本来就不一样。

**② `set(a) | set(b)`** —— 集合并集
```python
set([20,19,21,17,18]) | set([18,17,20,19,21])   # → {17,18,19,20,21}
```
`|` 在这里不是「或」，是把两个集合合起来去重。==必须用并集，只用某一路就会丢掉另一路独有的召回==，等于白跑那一路。

**③ `lambda x: x[1]`** —— 一次性无名函数
```python
fused.sort(key=lambda x: x[1], reverse=True)
# 等价 JS：fused.sort((a, b) => b[1] - a[1])
```

###### `enumerate` 的拆包方向（最容易记反）

`enumerate` 产出的顺序是**「序号在前、元素在后」**，这是固定的：

| 步骤 | 数据 |
| --- | --- |
| `vec_rank`（已是名次顺序） | `[20, 19, 21, 17, 18]` |
| `enumerate(..., start=1)` 产出 | `(1,20), (2,19), (3,21), (4,17), (5,18)` |
| `for pos, idx in ...` 拆包 | `pos` 依次 = 1,2,3,4,5；`idx` 依次 = 20,19,21,17,18 |
| 输出 `vec_pos` | `{20:1, 19:2, 21:3, 17:4, 18:5}` |
| 之后怎么用 | `vec_pos[20]` → `1`（块 20 排第 1） |

- `pos` 是**变量名**（position 缩写），不是关键字，换名字不影响结果。
- `enumerate` 给的是「**名次 → 块**」（1 号是谁），而我们要查的是「**块 → 名次**」，所以冒号两边要反过来写 `{idx: pos}`。
- ==写成 `{pos: idx}` 语法不报错，但结果是 `{1:20, 2:19...}`，后面 `.get(块下标)` 永远查不到，程序会悄悄错==。

| 块 | 向量名次 | BM25 名次 | 怎么算的 |
| --- | --- | --- | --- |
| 16 | 1 | 3 | `1/61 + 1/63` |
| 12 | 3 | 2 | `1/63 + 1/62` |

##### 4. 零件：rerank

```python
def cross_score(query: str, text: str) -> float:
    """
    交叉编码器占位：真模型是「把问题和文档拼成一条送进模型输出相关分」。
    这里先用词重合率顶替（0~1），**接口不变**，换真模型只改函数体：
        resp = httpx.post(f"{BASE_URL}/rerank", json={"query": query, "doc": text, ...})
        return resp.json()["score"] / 100
    """
    q = set(tokenize(query))
    d = set(tokenize(text))
    if not q:
        return 0.0
    return len(q & d) / len(q)


def rerank(query: str, candidates: list, top_k: int = 3) -> list:
    """对粗排候选逐条重打分，按 cross_score 降序取前 top_k（保留原有字段）。"""
    for c in candidates:
        c["rerank"] = cross_score(query, c["text"])
    return sorted(candidates, key=lambda c: c["rerank"], reverse=True)[:top_k]
```

两个点：

- `len(q & d) / len(q)`：`&` 是**集合交集**（两个集合都有的元素），除以 `len(q)` 得到「query 的词有几个在文档里出现」的覆盖率，取值 0~1。
- **为什么接口要保持 `(query, text) → float`**：真交叉编码器的输入就是「一对文本」，所以占位版必须同签名。以后换真模型只改函数体，`rerank()` 一行都不用动 —— 这就是「rerank 是可插拔的一层」。

##### 5. Retriever 与 hybrid_search（今天的核心产出）

```python
class Retriever:
    def __init__(self, chunks: list):
        self.chunks = chunks
        self.vectors = embed([c["text"] for c in chunks], type_="db")
        self.index = faiss.IndexFlatIP(self.vectors.shape[1])
        self.index.add(self.vectors)

    # ---- 纯向量检索（对照组）----
    def search(self, query: str, k: int = 3) -> list:
        ids, scores = self._search_ids(query, k)
        return [{**self.chunks[i], "score": s} for i, s in zip(ids, scores)]

    def _search_ids(self, query: str, k: int):
        """返回 (块下标列表, 分数列表)，按分数从高到低。"""
        q = embed([query], type_="query")
        scores, ids = self.index.search(q, k)
        return [int(i) for i in ids[0]], [float(s) for s in scores[0]]

    # ---- 混合检索 + 精排 ----
    def hybrid_search(self, query: str, recall_k: int = 5, top_k: int = 3) -> dict:
        # ① 向量粗排
        vec_ids, vec_scores = self._search_ids(query, recall_k)

        # ② BM25 粗排
        tokens = {i: tokenize(c["text"]) for i, c in enumerate(self.chunks)}
        bm = bm25_scores(query, tokens)
        bm_ranked = sorted(bm.items(), key=lambda kv: kv[1], reverse=True)
        bm_ids = [i for i, _ in bm_ranked[:recall_k]]
        bm_map = dict(bm)

        # ③ RRF 融合
        fused = rrf_fuse(vec_ids, bm_ids)
        pos_v = {idx: p for p, idx in enumerate(vec_ids, start=1)}
        pos_b = {idx: p for p, idx in enumerate(bm_ids, start=1)}

        # ④ 融合前后名次对比表（给人看的证据）
        table = []
        for rank_after, (idx, s) in enumerate(fused, start=1):
            table.append({
                "idx": idx,
                "向量名次": pos_v.get(idx, "—"),
                "BM25名次": pos_b.get(idx, "—"),
                "bm25分": bm_map.get(idx, 0.0),
                "rrf": s,
                "融合名次": rank_after,
                "source": self.chunks[idx]["source"],
                "片段": self.chunks[idx]["text"][:36].replace("\n", " "),
            })

        # ⑤ 取前 recall_k 个当精排候选；向量分查表补上（BM25 独有候选没有向量分 → 0）
        vec_score_map = dict(zip(vec_ids, vec_scores))
        cands = []
        for idx, _ in fused[:recall_k]:
            c = dict(self.chunks[idx])
            c["idx"] = idx
            c["score"] = vec_score_map.get(idx, 0.0)
            c["bm25"] = bm_map.get(idx, 0.0)
            c["rrf"] = next(s for i, s in fused if i == idx)
            cands.append(c)

        # ⑥ 精排
        hits = rerank(query, cands, top_k=top_k)

        return {"hits": hits, "max_vec": max(vec_scores) if vec_scores else 0.0, "table": table}
```

###### 整体是「宽召回 → 窄精排」的漏斗

```text
query
 ├─① 向量粗排  recall_k=5  → vec_ids    [20,19,21,17,18]
 ├─② BM25 粗排 recall_k=5  → bm_ids     [18,17,20,19,21]
 ├─③ RRF 融合            → fused       [(20,0.0323), (18,0.0318), ...]
 ├─④ 生成对比表           → table       5 行（给人看的证据）
 ├─⑤ 转成块 dict          → cands       5 个候选
 └─⑥ rerank 精排 top_k=3  → hits        3 个最终结果
```

| 步 | 输入 → 输出 | 真实数据 |
| --- | --- | --- |
| ① | query → 向量 top5 | `vec_ids=[20,19,21,17,18]`、`vec_scores=[0.8953, 0.6288, 0.5570, 0.4872, 0.4141]` |
| ② | query → BM25 top5 | `bm={0:3.2, ..., 18:16.21}`（22 块全打分）→ `bm_ids=[18,17,20,19,21]` |
| ③ | 两个名次表 → 融合榜 | `fused=[(20,0.032266),(18,0.031778),(17,0.031754),...]` |
| ④ | fused → 5 行 dict | 每行含「向量名次 / BM25名次 / rrf / 融合名次」 |
| ⑤ | fused 前 5 → 候选 dict | 向量分靠 `vec_score_map.get(idx, 0.0)` 补，BM25 独有的块给 0 |
| ⑥ | 5 候选 → 3 结果 | 按 `cross_score` 重排 |

###### 4 个设计决策（面试就讲这 4 条）

| 决策                                      | 为什么                                                              |
| --------------------------------------- | ---------------------------------------------------------------- |
| **粗排 5 → 精排 3**                         | 粗排宽是为了「**别漏**」，精排窄是为了「**排对**」；候选太少 BM25 的补救就没机会                  |
| **拒答用 `max_vec`，不用 `hits[0]["score"]`** | 融合后 top1 可能是 BM25 单独召回的块，它的向量分是 0，按它判会==误拒答==。这是加了 BM25 之后必须改的判据 |
| **遍历并集不是交集**                            | 只用 `vec_ids` 会丢掉 BM25 独有召回的块，等于白跑 BM25                           |
| **返回 dict 而不是 list**                    | `hits` 是结果、`max_vec` 是判据、`table` 是证据，三样用途不同                      |

###### 两个追问的标准答法

**Q：既然 BM25 在别处已经排过序了，为什么这里还要重排一次、不能直接取前五个？**

A：分两点。
1. **向量那一路确实没重排**——`_search_ids` 一次给出有序的 `vec_ids`，直接复用。BM25 那一路是**第一次算**（`bm25_scores` 之前从没被调用过），没有「之前的排名」可拿。
2. **打分 ≠ 排序**：`bm25_scores` 返回的是 22 块全部分数，字典顺序是插入顺序（0,1,2...21）而不是分数顺序，不 `sorted` 就不知道谁是前 5。要省这一步可以用 `heapq.nlargest(5, ...)`，但 22 个元素的排序是微秒级，省下来毫无意义。

**Q：真正重复的计算在哪？**

A：在验收 runner 里——`r.search(q, k=3)` 和 `hybrid_search()` 各算了一次 query 的 embedding（两次 API 调用）。这是**为了同时展示对照组和实验组**，生产代码只会调一条路。

#### RRF

表示向量检索和BM25检索的融合层。混合检索是整套策略，RRF 只是其中最后一步“合并”的算法。
```text
混合检索 = ① 向量路跑一遍 ─┐
                         ├─→ ③ 融合（RRF 只是融合的方法之一）
           ② BM25 路  跑一遍 ─┘
```
关系三层：
- 混**合检索（策略层）**：两条路都跑，结果合起来。你脚本 :199-200 说得很准：“两路都跑一遍，再把两份结果合起来。怎么合是下一步”。
- **RRF（融合层）**：回答“怎么合”的一种答法。公式 score = Σ 1/(k+名次)，把名次当通用货币（:214、:225 里 k=60）。
- **BM25 / 向量（检索层)**：两台发动机，管“怎么各自打分”。

##### 流程

RRF 全称 Reciprocal Rank Fusion。中文叫「倒数排名融合」，人话：每篇文档的得分 = 它在各路里名次的倒数和，名次越靠前，得的那一份越大。
###### 1. 流程图

同一句模板写两遍：按第二项（分数）降序，产出名次表。

```python
vec_pos = {k: i for i, (k, _) in enumerate(vec_rank, start=1)}
```
字典推导式 + `enumerate(start=1)`：遍历排好序的 (文档, 分数) 元组，`_`扔掉分数，`i` 当名次。这是整个 RRF 的关键转折点——从这行起，0.79 和 6.02 这些不可比的数字消失了，只剩 1、2、3、4 这种无量纲名次。
>下划线是「这个位置我不要」的约定

**④ 核心打分循环（:225-236）**
```python
K = 60
rrf = {}
for k in DOCS: # 遍历的是文档全集，不是某一路的名单
    a = 1.0 / (K + vec_pos[k])  # 向量路贡献：名次越靠前 → 倒数越大
    b = 1.0 / (K + bm_pos[k])   # BM25 路贡献
    rrf[k] = a + b       # 相加 = 「两路都说你好」的奖励
```

**⑤ 输出（:239）**
```python
sorted(rrf.items(), key=lambda kv: kv[1], reverse=True)   # 第三次 sorted，得最终榜
```

###### 4. 四个值得记住的工程细节

1. 分数三次转换：原始分 → 名次（③）→ 倒数分（④）→ 名次（⑤）。RRF 的输入输出都是"榜单"，它本质是榜单的代数运算，跟分数绝对值无关。
2. **k=60 的作用**：==压平差距==，==让融合更"民主"==。1/(60+r) 对 r=1 和 r=60 差 2 倍；不取 k 直接 1/r 的话第 1 名的分是第 60 名的 60 倍，头部会碾压全场。追问环节：291-293 的标准答案就是这个。**完整四档对比表（k=0 / 10 / 60 / 1000 的头尾倍率）见文末「追问补充 · RRF 的 k 为什么取 60」。**
3. 循环遍历 DOCS 而非 bm_rank：保证 4 篇全有分。真实工程里某路没召回的文档，那一路贡献记 0——这就是 :246-248 说的"BM25 里 0 分的 D，向量第1的优势被砍半"。
4. 并列分靠稳定排序解决：A/B/D 三家 BM25 全是 0，sorted 是稳定排序，按字典插入序 A,B,D 定名次——纯属副产品，正如 :161-162 所说"没有信息量"。

一句话：RRF 这 10 行代码 = 三次排序 + 一次名次加权和，全段的灵魂在 :216-217 那两行字典推导——把不可比的分数换成可比的名次，融合才有了共同语言。

### 面试话术
##### 问：你的 RAG 为什么要做混合检索？

答（三句话，一句一个理由）：

1）纯向量检索对「精确字符串」不敏感 —— 型号、订单号、错误码、人名这类字面，压成向量时会被整篇文档的语义稀释掉，召不回来。

2）BM25 是关键词算法，只看字面重合和词的稀有度，恰好补上这一块；但它不懂同义改写（用户说「画图」，文档写「扩图」，它就瞎了）。

3）所以两路都跑，用 RRF 按名次融合 —— 因为两路分数量纲不同，没法直接加权求和，RRF 用名次把量纲抹平了。

##### 追问1：RRF 的 k 取多少？为什么？

答：k=60 是经验值。它的作用是压平名次差距 —— k 越大，第 1 名和第 10 名的

得分越接近，融合越「民主」；k 越小越偏向单路头部结果。一般不用精调。

（四档具体数字见文末「追问补充 · RRF 的 k 为什么取 60」，这里只留结论。）

##### 追问2：混合检索的代价是什么？

答：多维护一套索引（倒排索引）+ 多一次查询，延迟和存储都涨；而且多了一组要调的参数（RRF 的 k、或加权时的两个权重）。所以只有语料里确实存在大量精确字符串（型号/编号/专有名词）时才值得上。

 ##### 追问3：RRF 之后还需要别的吗？

答：需要精排（rerank）。RRF 只看名次，不看「这篇到底多相关」，所以融合后的 top-k 还要再走一次交叉编码器重排 —— 这就是下一步

#### Rerank

它回答四个问题：

  1. 双塔（bi-encoder）为什么快？它把什么信息弄丢了？
  2. 交叉编码器（cross-encoder）为什么准？为什么慢？
  3. 为什么工程上要用「先粗排 20 个、再精排 3 个」这个两段式？
  4. rerank 救不回来的情况是什么？（面试必问）

##### 是什么

上一章的**混合检索**（向量 + BM25 + RRF）干的事，工程上叫「召回」（recall）。召回的目标是「别漏」，所以宁可多捞一些，通常捞 top-20~50。但 LLM 的上下文塞不下 20 段，你只能给它 3~5 段。于是问题变成：这 20 个里，到底哪 3 个最该给模型看？

→这一步叫「精排」（rerank，全称 re-ranking，中文：重排序）。

##### 第一步：双塔

第 1 步：双塔（bi-encoder，双塔编码器）—— 「==各算各的，最后比一比==」

双塔（bi-encoder）就是 day5 里用的那种“问题、文档分开各编一个向量，再**比余弦**”的架构——两座“塔”里各自灌一个向量，所以叫**双塔/双编码器**。
![[day6-混合检索（BM25+RRF）+ Rerank + 评测指标-1793185812764.webp]]

双塔编码器的做法：
1. 每篇**文档**单独送进模型 → 压成一个向量 → **存进向量库**（这是离线做的，一次）
2. 用户提问时，只把「**问题**」送进同一个模型 → 得到一个向量
3. 两个向量算个余弦相似度，就是相关分

为什么快：**文档那一侧是提前算好的**，查询时只算 1 次问题向量 + 20 次乘加。 20 篇文档的成本几乎等于 0，1 万篇也一样。

##### 第二步：双塔的bug

它丢了什么：问题向量和文档向量是「==分开算==再相比」的，模型在编码问题时根本不知道要跟哪篇文档比。更糟的是，一篇文档无论多长，最后都被压成**一个**向量——400 字里只有一句话相关，那句话的信息会被另外 380 字稀释掉。

![[day6-混合检索（BM25+RRF）+ Rerank + 评测指标-1793185703005.webp|425]]

##### 第三步：交叉编码器

交叉编码器（cross-encoder，交叉编码器）—— 「问题和文档**拼在一起，逐字对看**」。

所以慢：双塔的文档计算向量是离线提前算好的，而交叉需要问题和文档一起计算，但是问题是即时性的，所以每次都要重新计算

![[day6-混合检索（BM25+RRF）+ Rerank + 评测指标-1793186331329.webp]]

**核心矛盾**：双塔/向量检索快但不准（长文档稀释），交叉编码器把 query+文档拼一起过模型所以准、但慢 → 所以工程上是两段式"粗排20 → 精排3"（:121-127：走闭环不行漏撒，走精排负责排对，LLM 负责说人话）
```text
「双塔」bi-encoder（检索用的）        「交叉」cross-encoder（rerank 用的）

问题 ──→ [ 编码器塔A ] ──→ 向量q      问题 ┐
                                        ├─→ [ 一个编码器 ] ──→ 直接出一个"相关度"分数
文档 ──→ [ 编码器塔B ] ──→ 向量d      文档 ┘
              ↓                         ↓
      cos(q, d) 余弦相似度              问题在“看”文档时在场
```
注意：两塔是同`一个BERT/同一个bge`，`两套拷贝`，箭头没有交叉点。

|           | 双塔                                           | 交叉编码器                      |
| --------- | -------------------------------------------- | -------------------------- |
| 问题与文档是否交互 | 全程不交互，各编各的（:67）                              | 从第一层就拼在一起互相“看”（:93）        |
| 语料库如何加速   | 文档向量可提前算好存库，查询时只算问题那 1 次塔，~10ms              | 每次都要过完整模型，20个候选 = 20 次前向传播 |
| 代价        | 整篇文档几百字被压成一个向量（:47 “双塔的 bug”）——型号、错误码这类细节被稀释 | fine-grained，但快不起来         |
| 适用场域      | 几十万文档 → 毫秒级粗排（recall）                        | 精排 top-20 附近（排对/precision） |

所以整个系统的分工是：
- 双塔（或 BM25）当 召回层：在几十万文档里"不漏"，把候选缩到几十个；
- 交叉编码器当 精排层：在这 20-50 个里“排对”，砍到 top-3。
一个比喻（来自您文件 :189 的那句金句）：双塔是“撒网”，交叉编码器是“挑鱼”。信号不好没有鱼、或者鱼不够多样化时才算精准，但再遍历那张网也网不到海里的另一条好鱼。

##### 第四步：两段式
```text
     用户问题
        │
        ├─ ① 召回（要快、要全）：向量检索 + BM25 → RRF 融合
        │     从 1 万块里捞出 top-20          ← 10~50 ms
        │
        ├─ ② 精排（要准）：交叉编码器把 20 个挨个打分，重排
        │     取前 3~5 个                      ← 300~600 ms
        │
        └─ ③ 生成：把 top-3 塞进 prompt，让 LLM 看着答

一句话记住分工：
      召回负责「不漏」，精排负责「排对」，LLM 负责「说人话」。
```

##### 第五步：rerank救不回来的情况

rerank 的边界 —— 它只能重排，不能召回

>召回（要快、要全）：向量检索 + BM25 → RRF 融合

假设真正装答案的那一块文档，在召回阶段根本没进 top-20。上面 20 个候选挨个交给交叉编码器，它给出的最高分也只有 0.32（全是垃圾）。

你取前 3 名喂给 LLM → 答错。

❌ 这时候换更贵的 rerank 模型没用，因为答案压根不在候选集里。
✅ 要修的是召回这一步：==换 embedding 模型== / ==调切分== / ==加混合检索== / ==加查询改写==。

###### 幻觉
>幻觉（刚刚xhs正好刷到一个携程agent面试题里面提到如何减少幻觉）

不对——你描述的那件事（“==相似度高但不是答案”）不是幻觉==，它叫==答偏==/==噪音==，发生在检索层；
line 148 说的幻觉发生在生成层（LLM 说话那一步）。![[day6-混合检索（BM25+RRF）+ Rerank + 评测指标-1793199157560.webp]]

这两个是不同模块的两种病：
```text
检索层（向量/BM25/rerank 的地盘）          生成层（LLM 的地盘）
─────────────────────────            ─────────────────────────
相似度高 ≠ 能回答                          拿到 3 段上下文后自己编
「看起来相关其实是噪音」被排到前面           答案不在给定原文里就**脑补**
   ↓                                        ↓
 = 答偏 ← rerank 能部分缓解               = 幻觉 ← rerank 管不着
```
拆开说：
幻觉的准确定义：==LLM 生成了给定资料不支撑的内容==——**添油加醋**、**编数字**、把 A 型号规格用到 B 型号上。
注意它的发生位置：rerank 只决定“哪 3 段进 prompt"，LLM 拿到这 3 段之后怎么写是它自己的事。哪怕你精排完美、给的段落字字都对，**LLM 照样可能在末尾补一句原文里没有的“建议每年返厂检测”——这就叫幻觉**。
而“向量相似度高误以为是答案”，在脚本里对应的是 :147 那句「看起来相关但其实是噪音」：
- 双塔只算“整体画风像不像”，找出的候选可能只是“碰巧相似的闲聊”，真正含答案的一句话没进名单；
- rerank 甚至可能把这种噪音往前提（这是 :148 前半句的原话）。
这就是为什么脚本敢说「rerank 不减少幻觉，只减少答偏」——它的职权范围到“挑出哪 3 段”为止，LLM 看完之后说不说谎，它管不了。

幻觉要靠什么（:148 后半句给的两个药方）：
1. prompt 约束——例如“仅依据以下资料作答，资料中没有就明确说‘不知道’，禁止编造”，**从指令上锁住 LLM**；
2. 忠实度评测（**faithfulness**，如 RAGAS 那套）——生成完把答案拆成一句句断言，逐句核对“这句在上下文里有没有依据”，没依据的比例就是幻觉率，用它回归测试。

一句话总结两层病：答偏 = 找错了资料（检索层病，rerank 看病）；幻觉 = 拿着资料说梦话（生成层病，prompt 约束看病 + 忠实度评分量病）。顺便从流程上讲——若让 LLM 独自凭空硬答，幻觉会被放大；但幻觉和他自己的 RNG 而非你的检索层有关。

#### 追问补充（10-29 补齐）

##### K1 和 B 两个数到底管什么

公式里它们各管一块：

```text
score = Σ idf(t) ×  tf×(k1+1) / ( tf + k1×(1 − b + b×dl/avgdl) )
                    └─ 分子分母都被 k1 管 ─┘  └── b 只出现在这里 ──┘
```

一句话记忆：**k1 管「同一个词出现几次后不再加分」，b 管「文档长了打几折」。**

**k1 = 1.5（词频饱和速度）** —— 把文档长度设为平均水平（`dl/avgdl = 1`），只剩 tf 的影响：

| 词在本文出现次数 tf | k1=0 | **k1=1.5** | k1=5 |
| --- | --- | --- | --- |
| 1 次 | 1.000 | **1.000** | 1.000 |
| 2 次 | 1.000 | **1.429** | 1.714 |
| 3 次 | 1.000 | **1.667** | 2.250 |
| 5 次 | 1.000 | **1.923** | 3.000 |
| 10 次 | 1.000 | **2.174** | 4.000 |
| 100 次 | 1.000 | **2.463** | 5.714 |
| 上限（永远达不到） | 1 | **2.5** | 6 |

看 1.5 那一列：第 2 次出现贡献 +0.43、第 3 次 +0.24、第 10 次只贡献 +0.03，涨到 2.5 封顶 —— 这就是**收益递减（饱和）**。

- 为什么必须饱和：防止**关键词堆砌**，一篇把「保修」写 50 遍的文档不能因此排第一。
- `k1=0` 时 tf 项恒为 1，**完全不看次数**，只要出现过就满分。
- k1 越大越接近线性（明显奖励重复出现）。

**b = 0.75（长文档打折强度）** —— 长度因子 `f = 1 − b + b × (dl/avgdl)`：

| 文档长度比 dl/avgdl | b=0（不打折） | **b=0.75** | b=1（全打折） |
| --- | --- | --- | --- |
| 0.5（很短） | 1.000 | **1.290** | 1.429 |
| 0.8 | 1.000 | **1.099** | 1.136 |
| 1.0（平均） | 1.000 | **1.000** | 1.000 |
| 1.5 | 1.000 | **0.816** | 0.769 |
| 2.0（很长） | 1.000 | **0.690** | 0.625 |

- `b=0` 完全不罚长文档 → 长文档天然占便宜（词多 tf 就大）。
- `b=1` 按长度比例全罚 → 长文档只要内容更全就吃亏。
- `b=0.75` 是折中：==打 75% 的折、留 25% 余量==。
- 注意它是**双向**的：短文档 `dl/avgdl < 1` 时因子 > 1，**反而加分**（短文档词更集中，命中更有信息量）。

本项目真实数据（语料 22 块，平均 238.3 词）：

| 块 | 词数 | dl/avgdl | b=0 | **b=0.75** | b=1 |
| --- | --- | --- | --- | --- | --- |
| 17（型号一览） | 253 | 1.06 | 1.0000 | **0.9730** | 0.9644 |
| 18（含 12 个月） | 289 | 1.21 | 1.0000 | **0.9127** | 0.8868 |
| 20（报修流程） | 323 | 1.36 | 1.0000 | **0.8621** | 0.8243 |

块 20 比块 17 长 70 个词，同一个词同样出现 1 次，b=0.75 让它少拿 11% 的分。

**为什么不自己调**：k1 的行业区间 1.2~2.0（1.5 最常用）、b=0.75 是 Elasticsearch/Lucene 默认值，都出自 Robertson & Zaragoza 的 BM25。语料只有 22 块，==调参极易过拟合==，要动必须拿评测集说话。

> 面试口径：「k1 和 b 用行业默认 1.5 和 0.75。k1 控制词频饱和、b 控制长度归一化，我的语料只有二十来个块，调参没有统计意义；真要调得先有评测集做对比实验再动。」

##### RRF 的 k 为什么取 60

它调的是**名次差距被压平的程度**：

| 名次 | k=0（1/r） | k=10 | **k=60** | k=1000 |
| --- | --- | --- | --- | --- |
| 第 1 名 | 1.0000 | 0.0909 | **0.01639** | 0.000999 |
| 第 2 名 | 0.5000 | 0.0833 | **0.01613** | 0.000998 |
| 第 5 名 | 0.2000 | 0.0667 | **0.01538** | 0.000995 |
| 第 10 名 | 0.1000 | 0.0476 | **0.01429** | 0.000990 |
| **头尾倍率** | **10 倍** | 1.9 倍 | **1.15 倍** | 1.01 倍 |

三个极端都不行：

| k | 后果 |
| --- | --- |
| `0` | 第 1 名是第 10 名的 10 倍，单路的一家之言就能定胜负，==融合失效== |
| `60` | 头部只比尾部高 15%，单路极端判断被压平，两路都排中上的块才赢 |
| `1000` | 名次几乎无差别（1%），退化成「谁被两路都提到谁赢」，==排序信息全丢== |

k 的真实含义：**「最多只承认前 60 名有意义」**。

出处：Cormack / Clarke / Buettcher 2009 的 RRF 论文，在 TREC 数据集上试过；k 在 10~100 之间**结果差异很小（不敏感）**，60 是表现稳定的那个点，Elasticsearch、Weaviate、LangChain 的 `EnsembleRetriever` 默认都是 60。

> 面试口径：「60 是 RRF 原论文的经验值，作用是压平名次差距。k=0 时第 1 名是第 10 名的 10 倍，单路就能定胜负；k 上千名次之间几乎没差别，排序信息就废了。论文里试过 10 到 100 结果差异很小，属于不敏感参数，所以我没调。」

##### 项目里到底要不要手写 BM25

计划里技术栈写的是「手写 BM25」，但**手写的真实含义是「把 D6 这 25 行搬进项目」，不是重写**：

| 环节 | 用什么 | 为什么 |
| --- | --- | --- |
| 向量检索 | **FAISS**（库） | 底层 C++ 优化，自己写必慢 |
| Embedding | **API** | 模型是训练出来的 |
| **BM25** | **手写 ✅** | 纯算术、无依赖，是面试主考点 |
| Rerank | 先占位 `cross_score()`，以后换真模型/API | 模型没法手写，但**接口要自己设计** |
| RRF 融合 | **手写**（10 行） | 纯算术，面试爱问「为什么用名次不用分数」 |

手写 vs 库怎么选：

| | 手写（25 行） | `rank_bm25` 库 |
| --- | --- | --- |
| 代码量 | 25 行 | `pip install` + 3 行 |
| 面试价值 | **高**：能讲 df / idf / tf 怎么算 | 零：问原理只能答「我调了个库」 |
| 22 块规模 | 毫秒级 | 也是毫秒级，毫无优势 |

> 面试口径：「BM25 我自己实现的：切词后统计 df 算 idf，再用 tf 饱和函数加长度归一化打分，一共 25 行。没引库是因为知识库只有几十篇，自己写可控、也方便调参；**规模上百万才需要上 Elasticsearch**。」

##### print 对齐用的 `<4` `<9` `.3f` 是什么

f-string 里 `{值:格式}` 冒号后面那串：

| 符号 | 意思 | JS 对照 |
| --- | --- | --- |
| `<` | **左**对齐（右边补空格） | `padEnd(n)` |
| `>` | 右对齐 | `padStart(n)` |
| `^` | 居中 | 无直接对应 |
| `4` / `9` / `10` | 最小宽度占几个字符位（超了不截） | `padEnd(4)` 里的 4 |
| `.3f` | 浮点保留 **3 位小数** | `toFixed(3)` |
| `<9.3f` | 左对齐、宽 9、保留 3 位小数 | `toFixed(3).padEnd(9)` |

效果：

| 写法 | 值 | 输出（`·` 代表空格） |
| --- | --- | --- |
| `{18:<4}` | `18` | `18··` |
| `{0.0318:<9.3f}` | `0.0318` | `0.032····` |
| `{0.032266:<10.6f}` | `0.032266` | `0.032266··` |

- 宽度是为了**列能竖着对齐**。
- RRF 分保留 **6 位**是因为融合分差异只在小数点后第 5 位（`0.032266` vs `0.031754`），保留 2 位会全变成 `0.03`、看不出区别。==小数位数要按「差异出现在第几位」来定==。
- 一个坑：中文在终端占 2 个显示列，但 `len('块') == 1`，所以中文表头会错位 —— 终端固有问题，改用英文表头即可。
